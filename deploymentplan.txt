1. WHAT CHANGED IN THE CODE, AND WHY
--------------------------------------------------------------------------------

Five issues were found and fixed before deploying (commit 6cdf58a in
url-shortener-go). They are listed here because the deployment config
depends on them.

(1) REDIS ABSENT IS NOT THE SAME AS REDIS UNREACHABLE.
    The old plan said "Redis is optional — drop it", reasoning that the code
    degrades gracefully. It does, but not for free. With REDIS_ADDR left at
    its localhost default, every request dialed a dead endpoint and waited
    out the retries before falling back.

        measured: POST /api/links = 3.48s   (local Postgres, no Redis)

    The 1.8 panel renders that number as "ms round trip" on screen. It would
    have read 3500 ms. An explicitly empty REDIS_ADDR now means "no Redis",
    and the client is never constructed:

        measured: POST /api/links = 1.4ms

(2) REDIS TIMEOUTS ARE NOW BOUNDED.
    go-redis defaults to 3 retries with backoff. Both the cache and the rate
    limiter have correct in-process fallbacks, so a slow Redis is worse than
    an absent one. Dial/read/write are capped and retries disabled, taking
    the configured-but-down case from 3.48s to 0.82s.

(3) REDIS_URL IS NOW SUPPORTED, AND IS HOW UPSTASH CONNECTS.
    Upstash requires TLS. A "rediss://" scheme is the only thing that turns
    TLS on, and the old code only accepted host+password. Paste Upstash's
    URL into REDIS_URL and TLS is handled.

(4) THE DSN NO LONGER LEAKS INTO LOGS.
    repository.Open interpolated the raw DSN — password included — into both
    of its error strings, and the ping error is exactly the one that fires on
    a cold database. That would have landed in Cloud Logging in plaintext.
    Errors now carry a redacted DSN, keeping the host for diagnosis.

(5) THE COLD-START CRASH IS FIXED.
    Open pinged once with a 5s timeout and main called os.Exit(1) on failure.
    A suspended Neon takes longer than that to accept its first connection,
    so the process died on the first request after idle. The ping now retries
    with backoff inside a 30s budget. The /health warm-up is still worth
    having, but it is no longer load-bearing.

STILL TRUE FROM THE OLD PLAN:
  - No build step. frontend/static/*.wasm is committed. Pages build command
    stays EMPTY, output directory `frontend`.
  - GeoIP is genuinely optional. internal/geoip returns a no-op resolver when
    the .mmdb is missing. Skip MaxMind. Country shows as "" in analytics.

2. ARCHITECTURE — ONE DOMAIN, TWO HOSTNAMES, TWO PAGES PROJECTS
--------------------------------------------------------------------------------

  <domain>.com      -> Pages project #1  (Machine Room, output dir `frontend`)
  s.<domain>.com    -> Pages project #2  (redirect edge, output dir `redirect`)

Two hostnames is REQUIRED, not cosmetic. The shortener's redirect route is
`GET /:code` at the root. Sharing one hostname would make every unmatched
path on the portfolio — a typo, a missing asset — look like a short code.

Two PAGES PROJECTS (rather than a Worker, or DNS straight to Cloud Run):
  - deploys by git push, like everything else; no wrangler, no extra CLI
  - keeps the Cloud Run hostname out of DNS and out of the repo
  - certificates are Cloudflare's problem, already solved
  - both sit on the same free tier

  Browser -> Pages #1                          (wasm panels 1.4/1.5/1.7/1.13)
          -> Pages #1 /api/* -> Cloud Run      (panel 1.8)
          -> Pages #2 /:code -> Cloud Run      (actual redirects)
                                  |
                                  +-> Neon     (2 shards)
                                  +-> Upstash  (cache + distributed limiter)

WHY CLOUD RUN AND NOT FLY: Fly ended free resource allowances for new
organisations. A shared-cpu-1x would be ~$1.94/mo, roughly doubling the
annual cost. Cloud Run's free tier is documented and per-month, and this
service's Dockerfile already fits it: static CGO-free binary, non-root,
listening on 8080, which is the port Cloud Run injects.

WHY ASIA-SOUTHEAST1 AND NOT MUMBAI: Neon offers no Indian region — its
nearest is ap-southeast-1, Singapore. The database therefore cannot move,
so the compute has to follow it. Measured from Delhi: Neon Singapore
86-93ms, which becomes ~3ms once Cloud Run sits beside it.

Deploying to Mumbai instead would put every write across the bay twice —
the collision check and the insert — roughly 120-180ms per shortened link,
and that is precisely the number the 1.8 panel prints on screen.

The cache must follow the same logic. Upstash defaulted to a Mumbai region
here, ~55ms from Singapore, which would have made a cache read slower than
the database read it replaces. Co-locate it or switch it off; a cache
farther away than its database is worse than no cache.

Cost note: asia-southeast1 is Cloud Run Tier 2, ~20% above Tier 1 on
overflow. At free-tier volume that is $0 either way, and correctness of
placement beats a rate that never applies.

Buy the domain at CLOUDFLARE REGISTRAR: wholesale, no first-year promo, no
renewal jump. Namecheap/Porkbun win year one and lose from year two.
At cost, .com and .xyz land in the same band — take the .com. Avoid .io.

PRICES AND FREE TIERS DRIFT. Verify at checkout rather than trusting this
file. Render's free Postgres now expires after 30 days, which is why Neon
is used instead.

PHASE D — CACHE                                    ~5 min     $0
================================================================================

[ ] D1. Sign up at upstash.com (free tier, no card)

[ ] D2. Create a Redis database. Region: Mumbai (ap-south-1) if offered,
        otherwise match your Neon region.

[ ] D3. Copy the connection string and convert it to "rediss://" form.

        *** UPSTASH HANDS YOU THE WRONG FORM BY DEFAULT. ***

        The console shows a redis-cli snippet like:

            redis-cli --tls -u redis://default:<pw>@<host>.upstash.io:6379
                       ^^^^^          ^^^^^^^^
                       TLS as a FLAG  scheme says PLAINTEXT

        redis-cli takes TLS from the --tls flag. Go cannot: redis.ParseURL
        derives TLS from the SCHEME ALONE. Hand it redis:// and it connects
        in plaintext, Upstash rejects it, and the cache silently falls back
        to disabled — the service still works, just with no cache and no
        obvious error.

        Strip "redis-cli --tls -u " and add the second s:

            rediss://default:<pw>@<host>.upstash.io:6379

        Verified working: TLS negotiated, PING + SET/GET round trip, 37-41ms
        steady state from Delhi. First connection costs ~420ms for the TLS
        handshake; that is the pool warming, not the steady state.

[ ] D4. CHECK WHICH REGION IT LANDED IN. A cache is only worth having if it
        is closer than the database it fronts. If Neon is in Mumbai and
        Upstash is in Singapore, the cache is slower than the thing it
        caches and is worth turning off. Aim to put both in the same place.

Free-tier command limits apply. A portfolio demo will not approach them, but
check the current number at signup.

[ ] E3b. GRANT THE DEFAULT COMPUTE SA ITS BUILD ROLE. Do this BEFORE the
         first deploy or that deploy fails.

         Since Google's 2024 service-account change, a new project's default
         compute service account no longer receives build permissions. The
         first `gcloud run deploy --source` uploads the source, then dies:

             PERMISSION_DENIED: Build failed because the default service
             account is missing required IAM permissions ...
             IAM permission denied for service account
             <project-number>-compute@developer.gserviceaccount.com

         Nothing is wrong with the code — it never gets built. One grant:

             PROJ=$(gcloud config get-value project)
             NUM=$(gcloud projects describe "$PROJ" \
                     --format='value(projectNumber)')

             gcloud projects add-iam-policy-binding "$PROJ" \
               --member="serviceAccount:${NUM}-compute@developer.gserviceaccount.com" \
               --role=roles/cloudbuild.builds.builder \
               --condition=None

         Allow a minute for IAM to propagate, then deploy. Confirm with:

             gcloud projects get-iam-policy "$PROJ" \
               --flatten="bindings[].members" \
               --filter="bindings.members:${NUM}-compute@developer" \
               --format="value(bindings.role)"

[ ] E4. Deploy from the submodule directory. Cloud Run builds remotely, so
        Colima does NOT need to be running.

            cd 1.8-URL-Shortener/url-shortener-go

            gcloud run deploy url-shortener \
              --source . \
              --region asia-southeast1 \
              --allow-unauthenticated \
              --memory 512Mi \
              --cpu 1 \
              --min-instances 0 \
              --max-instances 3 \
              --set-env-vars "BASE_URL=https://s.<domain>.com" \
              --set-env-vars "DB_SHARD_0_DSN=<shard0 dsn>" \
              --set-env-vars "DB_SHARD_1_DSN=<shard1 dsn>" \
              --set-env-vars "REDIS_URL=<rediss:// url>"

        --max-instances 3 IS THE COST GUARD. Without a ceiling, a traffic
        spike or a crawler loop can scale out and generate a real bill.
        --min-instances 0 is what keeps it free when idle.

        If a DSN contains a comma, --set-env-vars will mis-split it. Use

================================================================================
4. WHAT TO EXPECT ONCE RUNNING
================================================================================

After a few minutes of no traffic Neon suspends and Cloud Run scales to zero.
The next visitor wakes both. The first request after idle pays a cold start:
the container starts in ~1-2s, and the ping retry added in fix (5) absorbs
Neon's wake without crashing. The /health warm-up in F6 fires this on page
load so a visitor rarely sees it.

Upstash does not suspend, so cache hits stay fast across idle periods.

If the cold start ever annoys you, --min-instances 1 removes it, but that
bills continuously and is no longer free. Do not set it casually.

KNOWN BEHAVIOUR: analytics are buffered in memory (ANALYTICS_BUFFER_SIZE,
default 2048) and flushed by a background goroutine. A scale-to-zero
shutdown can drop whatever has not flushed. Cosmetic for a demo.

5. ONGOING MAINTENANCE
================================================================================

Frontend change      -> git push. Pages project #1 redeploys automatically.
Redirect edge change -> git push. Pages project #2 redeploys automatically.
Schema change        -> run the SQL against BOTH shards.

CHAPTER WASM CHANGE (1.4 / 1.5 / 1.7 / 1.13) -> AUTOMATED.

  .github/workflows/rebuild-wasm.yml rebuilds and commits the bundles.
  The chain:

      push to a chapter repo
        -> its notify-portfolio.yml fires a repository_dispatch
        -> this repo runs "Rebuild wasm": advances the submodule pointer,
           runs frontend/build.sh, commits frontend/static/
        -> Cloudflare Pages sees the push and redeploys

  Three to five minutes end to end, most of it the Rust build.

  WHY THE ARTIFACTS STAY COMMITTED: the Pages build command is empty on
  purpose. Building inside Pages would mean provisioning Go, Rust and a
  version-matched wasm-bindgen in its image on every deploy, against a
  build-minute limit, for output that changes only when a submodule does.
  Building in Actions and committing the result keeps the Pages deploy to
  a file copy.

  NO BUILD LOOP: the workflow pushes with GITHUB_TOKEN, which by design
  does not re-trigger workflows. Pages is a git webhook rather than a
  workflow, so it still deploys.

  ONE-TIME SETUP, still to do:
    Copy .github/notify-portfolio.template.yml into each chapter repo as
    .github/workflows/notify-portfolio.yml, and add a PORTFOLIO_DISPATCH_TOKEN
    secret to each. Full instructions are in the header of that file.
    Until that is done, trigger a rebuild by hand:
      Actions -> Rebuild wasm -> Run workflow

  MANUAL FALLBACK (all the toolchain, locally):
      git submodule update --init --recursive
      rustup target add wasm32-unknown-unknown
      cargo install -f wasm-bindgen-cli --version <version in
        frontend/wasm-rs/Cargo.lock>
      ./frontend/build.sh
      git add frontend/static && git commit && git push

  WATCH FOR: build.sh downgrades a missing or version-mismatched Rust
  toolchain to a warning and skips 1.13, leaving the previous artifact in
  place. Locally that is silent. The workflow asserts the files exist so
  CI fails loudly instead.

BACKEND CHANGE (1.8) -> still manual, and a different pipeline. The wasm
  workflow does not touch it; url-shortener-go is a deployed service, not
  a bundle.

      cd 1.8-URL-Shortener/url-shortener-go
      git commit && git push
      gcloud run deploy url-shortener --source . --region asia-southeast1
      cd ../.. && git add 1.8-URL-Shortener && git commit && git push

  Automating this means giving Actions access to GCP — Workload Identity
  Federation (no stored key, preferred) or a service-account JSON in a
  repo secret. Not set up; deploying 1.8 by hand is a minute's work and it
  changes rarely.

Cloudflare Pages free tier: unlimited bandwidth and static requests. The
3.2 MB machine.wasm is lazy-loaded per panel, so the hero costs nothing.
Pages Functions run on the Workers free tier at 100k requests/day, shared
across both projects.
